# Offline logging and session upload

Status: implemented
Date: 2026-10-23
Updated: 2026-10-29

- **Offline**: session logging works without signal from the start (saved on the device, uploaded when online), since ranges often have poor reception; video uploads are queued the same way
- **Upload of sessions**: the app creates the ids (UUIDs) for sessions, ends, shots and volume entries, and uploads with idempotent `PUT`s: the session once, then each end with all its shots as soon as it is shot (so a coach sees results live, or as soon as the phone has signal again), so a retry never duplicates anything. The last write wins. The server recomputes every score from the position and returns its own values, which the app then shows. Coaches read sessions, they cannot change them, except for the sessions they log for an archer without an account. A coach's live view polls the session list (`/api/sessions/?updated_after=...`); push updates are not planned

## Sessions a coach opens, and two sessions for one training

- **Pull**: the phone also reads from the server (`pull` in `src/lib/log-sync.ts`) after sign-in, when the app comes back and when the connection returns, before it uploads. It takes `GET /api/sessions/gone/` (merged or deleted ids) and every session of yours that changed since the last pull, each with its ends and volume (one detail request per session, oldest change first; the first pull on a new phone fetches the whole history). They are stored without an upload (`keep`, so an empty one is not removed on leaving the screen), and what happens to a session the phone already has is the rule below. `updated_after` is the newest time the server sent, not the phone's clock. A pull that breaks off keeps what it fetched and goes on from there next time.
- **Two phones, one rule** (#84): last write wins per item (the session's own fields, each end with its shots, each volume entry), decided by the order of uploads, not by when the edit was made. On a pull, an item that has an op waiting in the queue is not overwritten (it goes up next and wins); every other item is replaced by the server's copy. An end or volume entry the server does not have, and that nothing waits for, is removed (it was deleted on the other phone; the server bumps `updated_at` of the session when an end is deleted, so the pull sees it). An item whose delete is queued does not come back. A session that is `gone` is left alone. The equipment of a session already on the phone is kept. A pull whose answer may predate an upload that finished meanwhile is dropped and done again at the next sync, otherwise the just-uploaded end would look deleted.
- **Not covered**: a session that the server deleted while results of it are waiting still asks the archer (see above). Changes to the session made on the other phone while this one has a queued change to the same session are decided as a whole: the queued session change wins for all its fields, not field by field.
- **Merge**: a coach can open an empty session for an archer (no type, no results) and the archer may start their own seconds later. The server merges the two (`server/training/merge.py`, [ADR 0004](../adrs/0004-merging-sessions.md)): media and notes move to the winner, empty fields of the winner are filled from the loser, the loser's id becomes a tombstone pointing at the winner. Only a session opened by someone other than the owner and without results can lose. Archer against coach: the archer's wins. Two coaches: the one with results, else the earlier start. Two sessions the archer opened never merge. A session with more than one possible partner is left alone.
- **Old ids**: `PUT`, ends, volume, media and notes under a merged id go to the winner; the `PUT` answers with the winner's `id`, and the phone renames its copy (and its queue, and queued media). A `PUT` to a deleted id answers 410. The phone drops the session, unless results of it (ends, volume) were still waiting to upload: then it keeps the session marked `gone`, stops uploading it, and the sync banner offers "Keep as a new session" (new id, session and all results queued again) or "Discard" (#84). `DELETE` of a merged id answers 204 and deletes nothing.
- **Past sessions**: a session started after the fact (`NewSessionView`, #89) is created finished: `ended_at` is `started_at` plus a chosen duration, never later than now, so it is never live and its merge window is `started_at` to `ended_at`. The app refuses a start in the future and more than 31 days back (`src/lib/session-time.ts`); the server only refuses an `ended_at` before `started_at`, so a phone with a clock slightly ahead is not refused for good. "Reopen" is hidden for a session that started more than 4 hours ago (the merge cap for open sessions). Times are stored in UTC with `Z`, which `sessionRows` relies on when it sorts.
- **Coach writes**: a coach who opened a session may change its times and notes (not type, ratings or equipment). After a merge their repeated `PUT` only fills empty fields. The results stay the archer's.

- **Moving queued media (#91)**: media on the phone can be moved to another session (or out of one) before it is uploaded; the queue item's `session` changes. A move while the upload runs is the one case that needs care: the request already carries the old session. `afterUpload` compares the sent item with the current one; if the session changed, the item stays in the queue as `uploaded` (its files are removed only when it leaves the queue) and the next request is a `PUT` with `session` (and `note`) only, no files. `drainMedia` sends it in the same run.

## Equipment made offline

- **`PUT /api/bows/<uid>/` and `/api/arrow-sets/<uid>/`** create or update an item by the uid the app gave it, and are safe to repeat: the same values add no revision. The body is the item plus an optional `revision_uid`, the uid the app gave the revision these values make; it is used when the values are new, so the app can name a revision before the server has seen it. The owner is the caller; an item of somebody else (a coach included) is answered 404 and left as it was. A `revision_uid` that belongs to another item is a 400. The integer routes are unchanged.
- **Sessions name equipment by uid**: the session `PUT` accepts `bow_revision_uid` and `arrow_set_revision_uid` besides the integer ids (not both for one revision), `null` clears. Equipment goes up before sessions, so the revision exists when the session names it (the upload order of the plan).

## Equipment on the phone

- **Store** (`src/lib/equipment-store.ts`, `useEquipment`): one file per account (`equipment:` key). An item has a `uid` made by the app, its tracked values, the active flag, and its revisions newest first, each with a uid made by the app. A change to a tracked value adds a revision (decimals compare as numbers, so "38" equals "38.0"); the active flag does not. The queue has one op per item; the body of the `PUT` is read from the current item when it is sent, so an edit made while waiting is included, and an edit made during an upload stays queued.
- **Upload** (`equipment-sync.ts`): `PUT /api/bows/<uid>/` (or arrow sets) with the values and `revision_uid`; the answer gives the server's integer id and the revision number it assigned, which the phone takes over. A delete uses the integer id and is queued only for items the server has; deleting one it never saw just removes it. A delete keeps a copy of the item in its op; if the server refuses it (409 for a bow used in a session), the item is put back in the list at once and the banner shows the reason ("Try again" takes it off the list again, "Give up" keeps it). Other refusals (400, 403) mark the op failed with the server's message; no connection, 401 or a server error end the run and keep everything for later.
- **Read**: the server's own bows and arrow sets are read after sign-in, when the app comes back and when the connection returns. Items with a change waiting keep the phone's version; items the server no longer has are removed unless they were never uploaded. An answer that was on its way while an upload finished is ignored, so it cannot bring back the values from before. Last write wins, as for sessions.
- **Sessions**: equipment is chosen by key (the uid; the integer id as text in a copy made before there were uids), and a session names it by the uids of its revisions when it has them, else by the integer ids as before (`Gear`). A session that names a revision still waiting to upload waits, and with it the sessions behind it (the queue keeps its order); the sessions go up as soon as the equipment has. A copy of the equipment that an older version kept in the log is used until the first item is made or read.
- **Not done**: a server that does not have #98 ignores `bow_revision_uid` and would store the session without equipment. Evaluations are not offline.

## Notes made offline

- **`PUT /api/notes/<uid>/`** creates a note by the uid the app gave it, or changes it, and is safe to repeat. The rules are those of `POST`; only the author can write, and a note of somebody else is answered 404 and left as it was. A photo, clip or session the server has not seen yet is a 400 on that field (`media`, `session`): the app takes that as "wait" and sends it after the photo or session has gone up. What a note is about (archer, session, end, photo, frame) cannot change after it is written; body, drawing and visibility can.
- **A note about yourself** (`archer` is you): no team, always private, nobody else reads it. A team or a visibility other than private is a 400. This is what an archer can write, and what a person without an account (#93) will upload when they make one.

## What a phone can read about photos, videos and notes

For the pull of media and notes (#83, #84); the app part comes after the server part.

- **Changes**: `Media.updated_at` is set by every save (upload, note, move into or out of a session) and by hand where the code uses `update()`: a session deleted (its clips stay, out of the session), two sessions merged, an account claimed. `GET /api/media/?updated_after=` and `GET /api/notes/?updated_after=` list what changed. Rows created before this have `created_at`.
- **Deletes**: `GET /api/gone/?kind=media|note&updated_after=` (`core.Tombstone`, [data-model.md](data-model.md)) tells a phone to drop its copy. It lists only what the signed-in person may have a copy of: their own clips, notes they wrote, and notes about them that were shared. Coaches read other people's data online only, so they get none for a clip of an archer they coach. Only the id and the time are kept.
- **Notes withdrawn**: a note shared with an archer that becomes coach only or private is a tombstone for the archer, so a copy on their phone goes.
- **Not covered**: notes deleted by their team being deleted, and a clip that changes owner through the transfer of an account (the old tombstones move with it, the clip's `updated_at` does not). Both are rare.

## Your photos and videos on the phone

- **The library** (`media-library.ts`, `useMediaLibrary`, a file per account under the `library:` key): the list of your own photos and videos as the server describes them (without the links, which run out after an hour), the ids whose thumbnail is on the phone, and where the last pull got to. Thumbnails are files in `Directory.Data/media-cache/<id>.thumb`, not in the queue's folder: they are copies and can be fetched again. The files themselves (full photos, videos) are not kept.
- **Pull**: after sign-in, when the app comes back and when an upload finished, `GET /api/media/?owner=<me>&updated_after=` and `GET /api/gone/?kind=media&updated_after=`, then the thumbnails that are missing (for items not in this pull, a fresh link is asked for). A failed download stops the round and is tried again at the next pull. Items still in the upload queue are not in the library; the screen shows the queue first.
- **Rule**: the server's copy replaces the library's, as there is nothing on the phone to protect (a change made on the phone goes through the queue or online). A deleted item leaves the list and its thumbnail file goes.
- **Screen**: `MediaView` shows the library when the server cannot be reached, for your own photos and videos (also of one session), with a line that says so. Tapping a photo shows its thumbnail, a video cannot be played (it streams). Coaches see other archers' media online only.
- **Account**: sign-out keeps the library under the account's key; deleting the account removes it and the thumbnails.
- **Cost**: a thumbnail is some tens of KB, so a thousand photos are tens of MB. There is no limit or cleanup yet.
- **Player for a queued item**: `/media/<id>` with the id of an item in the media queue plays it from its file on the phone (`MediaPlayerView`, `queued-clip.ts`). The queue id is the id the server will use, so the route does not change when the upload finishes. The player builds the clip from the queue item and object URLs of the stored files, and does not ask the server for it. The next and previous clips are the queued ones first, then the server's list. Deleting and moving work on the queue item. Your own queued items take notes and drawings: the note goes into the notes queue with the item's id and waits for the upload (`blocked` in `useNotes`), as for any queued note. In the player its text is in the sheet (under "waiting to upload", it can be taken back), its frame is marked on the tape and its drawing is shown on the picture (`waitingOnMedia`). Changing a waiting note means taking it back and writing it again. A queued item of an archer you coach (owner set) takes no notes until it is up, because the teams you may write in are not known on the phone; a line says so. When the item is up the server's list takes over.

## Notes on the phone

- **Queue** (`note-store.ts`, `useNotes`, a file per account, `notes:` key): a note written on the phone is saved on the device with a uid and goes up with `PUT /api/notes/<uid>/` (`note-sync.ts`). Once the server has it, it leaves the queue and the server's list shows it; the screens that show that list read it again when a note went up. Until then it is shown in the list as "waiting to upload" (`PendingNotes`) and can be taken back.
- **Order**: a note waits while its photo or clip is still in the media queue (and not yet up), or its session or end is still in the log queue. Other notes go on meanwhile. The check is in the app (`blocked` in `drainNotes`), not a 400 from the server, so a note on a photo that is gone does not wait for ever: it fails with the server's message and shows in the banner (retry or give up).
- **Failures**: 400, 403 and similar mark the note failed with the server's message; no connection, 401 or a server error keep it queued.
- **Not offline**: changing a note's text or drawing, deleting a note, and the teams a coach may write in still need a connection. Sign-out counts waiting notes, and deleting the account removes them.
- **Copy of the server's notes** (`note-library.ts`, `useNoteLibrary`, a file per account, `note-library:` key): the phone keeps the notes about you (your own, and those coaches shared with you) and those you wrote about others, as the server describes them. A pull after sign-in, when the app comes back and when a note went up asks `GET /api/notes/?archer=me`, `?author=me` (both with `updated_after`) and `GET /api/gone/?kind=note`. A coach does not keep the notes of others about their archers (they read those online), only their own. Notes in the upload queue are not in the copy; the screens show them from the queue. A list a screen reads from the server also updates the copy, and a note changed or deleted in the app changes it at once.
- **Reading offline**: when the server cannot be reached, the session notes, the notes under a photo in the media screen and "from your coaches" on Home list the copy, with a line that says so. Editing and deleting are hidden (`can_edit` and `can_delete` are false). A photo note shows the small picture the phone kept, if there is one. The session list matches `session`, and the notes about the event of the session that are in no session, like the server. The event screen and the clip player need the server for the event or the clip itself, so their note lists are not read from the copy.

## Without an account (#93)

- **State**: `useAuth().status` is `loading | signedOut | signedIn | local`. `local` is entered on its own by `useAuth` when the tokens and the flag are read and neither is there (first launch, tokens revoked) and by `signOut` (account deletion goes through it); the flag is kept as a flag (`local-mode`) and an owner id (`local-owner-id`) in Preferences (`useLocalMode`, `src/lib/local-mode.ts`). The store owner is `{ kind: 'local', id }`, so the log, equipment, notes and media queue live under `<store>:local:<id>`. The id is made once and never changes. Signing in or registering turns the flag off and moves the app to the account's keys; the local data stays under its own keys, is not shown while signed in, is not deleted and is **not uploaded**. Signing out finds it again.
- **No network**: in local mode nothing is sent. The uploads and pulls already wait for `signedIn`; the server check at start-up (`/api/health/`) also waits, and the units setting is not sent to a profile. The outbox keeps filling as it does for an account (one op per item, so it stays small): it is the list the later upload of a local archer starts from. The screens treat waiting and failed as zero in local mode.
- **Router**: `meta.auth` `'in'` lets `local` through; `'account'` (new) is for signed-in only and sends `local` to the start screen; `'out'` stays open to `local` so "Sign in or register" in Settings works. Team, agenda, evaluations, coach views of archers, account, profile, privacy and the server's session view are `'account'`.
- **The archer**: notes and media name their archer by number; without an account it is `LOCAL_ARCHER` = 0 (`Number(userId)` of nobody is 0). The upgrade upload has to map it to the account's id.
- **Statistics and the heatmap** are computed on the device from the sessions on the phone (`src/lib/stats.ts`), see [statistics.md](statistics.md). Scores come from `scoring.ts`, see [arrow-plotting.md](arrow-plotting.md).
- **Notes**: the notes store is the list. A note can be deleted, and on a photo its drawing changed; its text cannot be edited yet. A note about a photo is deleted with the photo.
- **Photos and videos**: `MediaView` lists the queue (nothing uploads, so nothing leaves it) and opens an item in `LocalMediaView` (`/local-media/:id`): the photo with its drawings, notes and "Draw", or the video in the browser's own player. The frame-by-frame player and notes on a frame need the server (`MediaPlayerView`).
- **Backup**: `LocalDataView` (`/settings/data`) exports sessions, equipment and notes (with drawings) as one JSON file (`src/lib/local-export.ts`, format `fletchr-local`, version 1) and imports it again. Import adds what the device does not have, matched by the ids the app made, and leaves everything else as it is; a file that is not ours, newer, or incomplete is refused whole. Photo and video **files are not in the file**.
- **What a person without an account does not get**: teams, coaches, evaluations, the schedule, sessions of other archers, sync between phones, video Wi-Fi setting, server address.
- **Not built**: uploading local data when an account is made or signed in to (decided by the maintainer: later), what happens when that account has its own data, editing a note's text, a local frame-by-frame player.
- **Android backup of app storage (to decide)**: the manifest has `allowBackup="true"` with no `fullBackupContent` or `dataExtractionRules`, so Android's Auto Backup uses its defaults. Capacitor's `Directory.Data` is the app's `filesDir` (checked in `@capacitor/filesystem`, `LegacyFilesystemImplementation.kt`) and Preferences is `shared_prefs/CapacitorStorage.xml` (checked in `@capacitor/preferences`), both inside the default scope: the log, equipment, notes, the queue, the owner id **and the queued photo and video files**. Auto Backup has a limit of 25 MB per app, after which no backup is made (Android documentation, from memory, not checked here); videos reach it quickly. Whether and when a restore happens on a new phone depends on the Google account's backup setting and on how the app was installed. So the JSON export stays the only copy the app itself controls. Options: leave it, exclude the media folder from the backup so the small stores fit, or turn the backup off for the app. Not changed.

## Where the data is kept

- **Owner and keys**: a store belongs to an owner (`src/lib/store-owner.ts`): an account on a server, or a person without an account (#93, see above). The key is `<store>:<server>:<userId>` for an account, which is what the log (`log:`) and the media queue (`media:`) always used, and `<store>:local:<id>` for a local owner. Another account on the same phone never sees the data, and it stays on the device when you sign out.
- **Files**: on a phone the log and the media queue are one JSON file each in `Directory.Data/stores/` (`src/lib/file-store.ts`, `dataStore` in `local-store.ts`), not in Preferences, where every key shares one SharedPreferences file on Android. A save writes a `.tmp` file and moves it over the old one; if the system refuses to rename onto an existing file the old one is removed first, and a leftover `.tmp` is read when the file is missing. A burst of changes writes only the newest value. The browser keeps using localStorage. Small settings (theme, language, units) stay in Preferences.
- **Sign-out and account switch**: nothing is wiped. The data of an account stays under its key and comes back when that account signs in again on this server; another account never sees it. Sign-out asks first when items are waiting (log, failed, queued media). Deleting the account removes its log file and its queued media with their files (`onAccountDeleted` in `useLog`).
- **Moving from Preferences**: the first read of a key that has no file reads the old Preferences value, writes the file, reads it back, and only then removes the Preferences value.
- **Unreadable data**: a stored value that is not valid JSON is copied to `<key>.unreadable` before the store starts empty, so the next save cannot destroy the only copy. Nothing shows this yet.
